# Opera 导航与目录设计

> **状态**：已定稿（owner 2026-08-14 逐条讨论确认）。
> **配套**：批次计划见 `docs/70-workplan/20-opera-ia-restructure.md`；
> 定位与域划分的上位依据是同目录 `opera-top-level-design.md`。
> **可视版本**：https://claude.ai/code/artifact/49e53a82-b5a2-467b-9a86-3d9a0ca69bd9

本文规定 opera 的分组、命名、状态机与探测纪律。它是**实施依据**——凡与本文冲突的
既有实现按本文改，不是反过来。

## 1. 为什么重构

改之前是 8 组 21 项，同一个侧栏里跑着**四套互不相容的命名体系**：

| 体系       | 实例                                                                                                                                     | 问题                          |
| ---------- | ---------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------- |
| 产品代号   | `Atlas · 模型服务` / `Runos · 能力服务` / `ships · 产品发布` / `trace · 运行监控`                                                        | 大小写都不统一                |
| 英文资源名 | `Endpoint` `Product Grant` `API Key` `Metering` `Capability` `Credential` `Grant` `Audit` `Metrics` `Logs` `RBAC` `Settings` `Dashboard` | 13 项，占一半以上             |
| 中文功能名 | `模型服务` `变更流水` `产品目录` `维护窗口` `服务监控` `任务调度`                                                                        | 6 项                          |
| 英文分组名 | `Observability` `Security`                                                                                                               | 与「总览 / 系统」同层不同语言 |

但**最该改的不是语言，是按产品代号分组**。`opera-top-level-design.md` §11 写着：

> Opera 不属于 Atlas。Opera 管理 Atlas。未来同样管理 Arda、Runos、Ruyin。

而侧栏把 Atlas、Runos 摆成分组名，读起来像 opera 是这两个产品的附属控制台。按
**管理域**命名才与那句立场一致，也才可扩展——将来第二家模型供给方接进来是进
「模型管理」，不是并列出一个新的产品代号分组。

此外还有三处重名：三个都叫「审计」的面（Atlas 变更流水 / runos Audit / security
Audit），以及两个几乎同名、却指向不同系统的 Grant。

## 2. 命名规则

### 规则一 · 中文主名 + 英文副名，同项两行

每个导航项**两行**：第一行中文功能名，第二行小字号英文原词。侧栏收起态两行都不显。

英文必须**留在项目里**，不能降级成描述行——`ShellNavItem` 只有 `{href, label, icon}`
三个字段，`NavItemRow` 只渲染 `label`；opera 自己扩的 `description` 字段**侧栏根本
不读**，所谓"保留在描述行"在界面上等于没有。

保留英文的理由（runos `280-management-apis.md` §1.3 原话）：

> 消费方可以自行改称谓，但运营者在审计事件里看到的是 `mgmt.grant.create`。
> **与 API 分叉的词表在控制台这头买到的清晰，会在两者相接的每一个点上还回去。**

### 规则二 · 产品代号后置且弱化

Atlas 与 Runos 是**独立产品**，opera 是它们的管理平面。代号出现在分组名**末尾**：
`模型管理 · Atlas`，不是 `Atlas · 模型服务`。前缀读起来像"这块属于 Atlas"，后缀才是
"这块管理 Atlas"。

> **DS 依赖**：`splitBrandTitle` 现按 `" · "` 拆开并把**前缀**染品牌色——它假设的正是
> "品牌在前"。代号后置需要它支持反向，否则会把"模型管理"当品牌名染色。

### 规则三 · 同类对象跨域必须可区分，且成对命名

「授权」「审计」这类词会在多个域各出现一次。规则是**对象名 + 对象名授权**，不靠分组
标题消歧——搜索、面包屑、收藏夹里都拿不到分组标题。

| 域       | 对象         | 授权         |
| -------- | ------------ | ------------ |
| 模型管理 | **模型**路由 | **路由**授权 |
| 能力管理 | **能力**注册 | **能力**授权 |

**为什么是「模型路由」**：Atlas 的 endpoint（`chat/default`）带 primary 与 fallback，
它本身就是一条**具名路由策略**——"入口"是抽象说法，"路由"说的是它实际在做的事；
"能力"二字则会与**能力管理**（Runos 域）撞，改"模型"既不跨域也更准。

**为什么不叫「授权管理」或「产品授权」**：前者与能力域的授权撞名；后者区分不了——
**两边主体都是产品**（Atlas 是 产品×路由，Runos 是 产品×能力），真正的区别在**授的是
什么**，不在授给谁。

## 3. 目标目录

7 组 21 项。两条分隔线编码的是「概览 → 四个管理域 → 两个通用面」这个真实分层。

```text
概览
  总览                Overview          /
─────────────────────────────────────────
模型管理 · Atlas
  模型服务            Model Service     /model/services
  模型路由            Endpoint          /model/routes
  路由授权            Product Grant     /model/grants
  调用密钥            API Key           /model/keys
  用量计量            Metering          /model/metering
能力管理 · Runos
  能力注册            Capability        /capability/registry
  凭证托管            Credential        /capability/credentials
  能力授权            Grant             /capability/grants
  用量计量            Usage             /capability/metering   [待建]
产品管理
  产品目录            Catalog           /product/catalog       [含上线流程入口]
  接入凭据            OIDC Client       /product/clients
  权益配置            Entitlement       /product/entitlements  [新建]
运行监控
  服务状态            Health            /ops/health
  运行指标            Metrics           /ops/metrics
  调用日志            Logs              /ops/logs
  任务调度            Jobs              /ops/jobs
  维护窗口            Maintenance       /ops/maintenance
─────────────────────────────────────────
安全审计
  变更审计            Change Trail      /audit/changes
  权限管理            RBAC              /audit/rbac            [跳转 admin]
系统配置
  系统配置            Settings          /settings
```

**不进导航但保留的页**（2026-08-14 落地时确定）：

| 路径                    | 为什么留                                       | 状态                            |
| ----------------------- | ---------------------------------------------- | ------------------------------- |
| `/capability/endpoints` | 端点嵌在能力里面，runos 没有独立的顶级列表接口 | 长期保留为说明页                |
| `/audit/atlas`          | B2 的过渡停靠点                                | B3 已下线，改跳 `?source=atlas` |
| `/audit/runos`          | B2 的过渡停靠点                                | B3 已下线，改跳 `?source=runos` |

后两者当时是**过渡资产**——B2 只做路径迁移不做审计面合并，把它们摆在 `/audit/*` 下而
不是留在 `/atlas/*` `/runos/*`，是为了在 B2 结束时旧前缀能一次清干净，不留半截。

## 4. 板块定位

定位写清楚，是为了让「新东西该放哪」以后有判据，不必每次重新讨论。

| 板块         | 回答什么                             | 边界                                                     |
| ------------ | ------------------------------------ | -------------------------------------------------------- |
| **概览**     | 现在有没有需要我立刻处理的事         | 任何需要"点进去改"的都不属于这里                         |
| **模型管理** | 平台能调哪些模型、经由谁、谁有权调   | 上游 Atlas `/capability/*`                               |
| **能力管理** | 业务 agent 除模型外还能做什么        | 上游 Runos `/capability/*` `/commerce/*` `/governance/*` |
| **产品管理** | 平台上跑着哪些产品、它们怎么接进来的 | 产品的**商业**封装（套餐/定价/订阅）归 admin             |
| **运行监控** | 系统现在与最近一段时间怎么样         | 无主机资源数据源，见 §7                                  |
| **安全审计** | 谁在什么时候改了什么                 | 权限本身归 admin，此处只出跳转                           |
| **系统配置** | opera 这个控制台自己怎么配           | 配的是**控制台**，不是被管理的系统                       |

## 5. 三个审计面：按性质分，不按产品分

| 来源                       | 内容                                              | 性质     | 去处     |
| -------------------------- | ------------------------------------------------- | -------- | -------- |
| Atlas `change_records`     | 每一次 `/capability/*` 写，含直连的与被守卫挡掉的 | 管理变更 | 安全审计 |
| Runos `mgmt_event`         | 管理面变更，带 `actor_console`                    | 管理变更 | 安全审计 |
| opera `support.audit_logs` | 只记经过 opera 的写                               | 管理变更 | 安全审计 |
| Runos `capability_call`    | 每次调用的延迟、裁决、结果                        | 运行事实 | 运行监控 |
| Runos `task_outcome`       | 任务自报结果                                      | 运行事实 | 运行监控 |

前三条回答同一个问题——**谁改了什么**。一次合规追溯不该需要先知道记录躺在哪个产品的
库里。后两条是运行事实，与请求日志、指标同类；把调用流水放进「安全审计」是把运行数据
错分成了问责数据。

**变更审计做成带来源切换的单页**（三个来源各一个 tab），**不做字段合并**——
`change_records` / `mgmt_event` / `audit_logs` 字段形状并不相同，合并需要映射层。看得到
"三处都在这儿"，但不假装它们是同一张表。

### 5.1 落地时定下的三条（2026-08-14，B3）

**tab 顺序**：平台 · opera → 模型面 · Atlas → 能力面 · Runos。平台那份在前，因为它是
唯一**跨域**的一份（模型面、能力面、产品登记，凡是经过 opera 的写都在里面），是「先看
哪儿」的答案；另外两个是「上游那边究竟看到了什么」的下钻，覆盖直连上游、绕过 opera
的写。

**`?source=` 进地址栏**（默认值不写）。审计场景里「把这一页发给同事」是常规动作，tab
状态不进 URL 的话发过去的永远是默认 tab。旧路径也靠它一跳到位：`/atlas/audit` →
`/audit/changes?source=atlas`，不让人落地后再点一次。

**未选中的 tab 不挂载**。三条流各打各的上游接口，全挂等于进页面就发三个请求、其中两个
的结果没人看。

## 6. 产品上线

### 6.1 为什么是「上线」不是「发布」

「发布」在本平台已有主——**admin 做套餐发布**（订阅 plan-version）。这条流程做的是
登记 → 配凭据 → 配授权 → 验证 → 转正式，产品因此变得**可运行**，不是**可售卖**；两者
都叫发布正是规则三要防的同词异义。「上线」的终点动作与目录里 `草稿 → 启用` 的状态
跃迁一一对应。

### 6.2 顺序：草稿先行，不是验证先行

「验证通过才入目录」**做不到**：验证的大部分项要求产品已经存在——OIDC 客户端挂在产品
上，模型路由授权与能力授权都按 `productCode` 配，权益信封按产品码读。产品码还没有，
就没有东西可验。

好在目录**本来就有草稿态**（新建即「已登记（草稿）」）。所以流程是：

```text
① 建草稿 → 拿到产品码
② 配置：OIDC 客户端 → 模型路由授权 → 能力授权 → webhook
③ 验证：逐项实测
④ 确认上线 → 草稿转正式
```

产品目录不是流程的产物，而是**同时装着草稿与正式**的台账；「确认上线」是那个跃迁。

### 6.3 草稿阶段是交接期，接入是双边的

平台侧配完之后有一批东西要**交给对方**，对方配完才谈得上验证。草稿页需要**交接信息**区：

| 交给对方                                   | 等对方做                             |
| ------------------------------------------ | ------------------------------------ |
| 产品码（= 授权主体、S2S 令牌的 `act.sub`） | 用它换票，调用里带对                 |
| `client_id` 与一次性 `client_secret`       | 存进自己的配置，不回显、丢了只能轮换 |
| webhook 签名密钥、回调地址要求             | 实现接收器并验签                     |
| 各能力域的接口基址与契约文档               | 按契约实现调用                       |

这也是**草稿必须持久、失败不回滚**的原因：等对方可能是几天的事，不是"重试一次"。

### 6.4 状态机：两个状态，不是一个

**生命周期状态**（落库）与**验证态**（最近一次实测结果）必须分开。合成一个字段立刻
出问题：上线半年后一次复验失败，难道把一个在跑的产品自动改回草稿？

这与本仓反复出现的同一条原则一致——**意图与后果分列**（模型路由的 `isActive` 与
`resolution` 也是两个字段，且只在上游坏掉时才分叉）。

**生命周期与动作**

| 动作     | 从                     | 到     | 前置条件                               |
| -------- | ---------------------- | ------ | -------------------------------------- |
| 登记产品 | —                      | 草稿   | 产品码唯一。登记即入目录，只是标着草稿 |
| 确认上线 | 草稿                   | 已上线 | **点击时自动重跑验证，全通过才跃迁**   |
| 停用     | 已上线                 | 已停用 | 可逆。不影响已配的授权与凭据           |
| 恢复     | 已停用                 | 已上线 | 提示重新验证——停用期间对方可能改过     |
| 退役     | 草稿 / 已上线 / 已停用 | 已退役 | **终态**，二次确认                     |

> **2026-08-14 落地时补的一条边**：`草稿 → 已退役`。原表只写了「已上线 / 已停用」，
> 但既然没有删除动作，一个谈崩了的草稿就会永远躺在目录里且无路可走。退役正是给它的
> 出口——「谈过、没成」本身就是要答得出的历史。

**没有「删除」**。退役是状态跃迁不是删行——「谁曾经接入过、什么时候退的」必须答得出。
与撤销授权迁 `revoked`、api-key 撤销保留行同一条规则。

**验证态**（不进生命周期状态）

| 验证态 | 含义                         | 运营者该做什么            |
| ------ | ---------------------------- | ------------------------- |
| 未验证 | 从未跑过                     | 跑一次                    |
| 待我方 | 有检查项卡在平台侧配置       | 去对应的授权 / 凭据页补配 |
| 待对方 | 平台侧齐了，失败项归因于对方 | 把交接信息与报告发给对方  |
| 通过   | 全部通过                     | 草稿态：可确认上线        |

刻意**不设「失败」这一档**：失败总是有归属的，「待我方」「待对方」既说明状态也说明
下一步，而「失败」两个字谁都不知道该动谁。真实错误文本在报告里，不在状态标签里。

**两条约束**

1. **确认上线时自动重跑验证。** 不接受"三天前通过"——配置随时会变，拿过期的通过去
   上线就是让声明冒充事实。重跑通过才跃迁，因此不必定义"结果新鲜度"。
2. **上线之后验证失败，不自动停用。** 只更新验证态、在目录行标出来。自动停用一个正在
   跑的产品，是把**监测信号**变成**破坏性动作**——与「撤销不是急停」「父级动作永不写
   子级」同源。要停由人来停。

### 6.5 入口与终态

| 入口              | 场景                                    |
| ----------------- | --------------------------------------- |
| 产品目录 · 主按钮 | 接入新产品——建草稿并进入流程            |
| 草稿行 · 继续接入 | 接了一半，回来续                        |
| 正式行 · 重新验证 | 对方改过了，或密钥轮换 / 授权变更后复验 |

**不常驻导航**：接入是低频动作，未完成的接入本来就以草稿行躺在目录里，从那行续比从
一个空流程页开始更自然。第三个入口尤其重要——它让验证不会变成"接入时通过"这样一个
永不更新的过期结论。

终态两个：**验证通过**（可点确认上线）/ **错误报告**（流程结束，草稿保留，按侧列出待办）。

### 6.5.1 五项检查的实际形状（2026-08-14 落地时订正）

批次计划原写「复用已有的 webhook test-delivery」——**那个能力全仓不存在**，是推演出来
的不是核对出来的。「不新造探针」的约束保留并从严：五项检查**全部读平台自己已有的状态，
一次外部请求都不发**。

| #   | 检查         | 判据                                                                                     |
| --- | ------------ | ---------------------------------------------------------------------------------------- |
| 1   | 产品登记     | 产品码存在；第三方接入必须填了接入方                                                     |
| 2   | 接入凭据     | 有启用中的 OIDC 客户端且配了回调。**只测我方注册**                                       |
| 3   | 模型路由授权 | 有生效中的路由。**过期的不算**——到期在读时判定，网关不会因为 `isActive` 还是 true 就放行 |
| 4   | 能力授权     | 有 active 授权（derived 同样算，它与 direct 等效）                                       |
| 5   | Webhook 登记 | 登记了回调地址 + 签名密钥引用。**只看登记，不发投递**                                    |

不发测试投递的两条理由缺一不可：它是对**对方生产端点**的真实请求；而且它测的是「这一刻
通不通」，运行监控里的投递队列本来就在持续回答这个问题。

**`token-exchange` 与 `C2 权益` 两项做不了**：前者需要产品的 `client_secret`，平台只有
哈希——**平台测不了对方换票**；后者 opera 侧没有任何 entitlements 读端点。两项连同 C3
计量与端到端验收，都留在接入检查单上由操作员按对方回报勾选。这条边界写在页面上，
不含糊过去——这也正是 §6.6「运营者代跑、报告可交付」成立的前提：报告如实说明哪些是
实测、哪些是转述。

### 6.6 不给对方开 opera 账号

需求是"给少量开发者验证，但不想让他看到更多"。在 opera 里开只读页**解决不了后半句**：

- opera 每一页都在管生产配置，为一个只读页开登录路径就是把误操作面扩大到该群体
- **侧栏本身就是信息**——即使点进去 403，导航也已告诉他平台有哪些能力域、接了哪些产品
- RBAC 归 admin，为此新造一个极少数人持有的能力码最容易变成没人记得的死码

**运营者代跑，报告可交付**：对方拿到带时间戳、分两侧、逐项结论的报告，不是控制台。
这与 opera 现有探测动作一致（模型自检、供应商验证都是运营者按需触发）。真要自助，
正确落点是面向开发者的界面，那是另一个产品决定。

## 7. 运行指标与探测纪律

### 7.1 顶层设计列的五项指标，一项数据源都没有

`opera-top-level-design.md` §7 把 Metrics 列为 **CPU / Memory / GPU / Network / Disk**。
这五项**目前全部没有数据源**——现有的全是服务级与调用级指标，没有任何主机/容器采集。

所以「运行指标」的诚实定位是：**自有服务与调用指标（真实数据）+ 基础设施指标的跳转
入口**（Kafka 等外部平台）。不自建主机监控，也不摆五个永远空着的资源图。

### 7.2 能拿到的，尽量全显示

| 来源                          | 能回答                                                      | 数据性质       |
| ----------------------------- | ----------------------------------------------------------- | -------------- |
| Atlas `logs/summary`          | QPS、错误率、延迟 avg/p95、Token 量；按模型/供应商/路由分组 | 窗口聚合       |
| Atlas `providers/performance` | 各供应商累计计数、在途请求、p50/p95                         | **累计计数器** |
| Atlas `readyz`                | 依赖就绪 + `registryDrift` 配置漂移                         | 状态快照       |
| Runos `audit/calls`           | 每次调用的延迟、裁决、错误类                                | 明细流         |
| Runos `usage-summaries`       | 七轴用量聚合                                                | 窗口聚合       |
| 平台 `product-health`         | 接入产品 prod/beta 存活与就绪                               | 探测结果       |
| 平台 job-scheduler            | 后台作业心跳、webhook 队列深度                              | 状态快照       |

`providers/performance` 是**累计计数器不是瞬时值**——算速率必须取两次做差。这本身就是
"低频取样"的理由，不是高频刷新的理由。

### 7.3 探测纪律

现有实现有一处**空转**：服务状态与任务调度两页各 30 秒轮询，都判了 `visibilityState`，
但判法是**定时器照跳、只跳过请求**——页面后台挂一小时，计时器仍醒 120 次。

要的是**真停**：隐藏时 `clearInterval`，回到前台重新起并**立即补一次**（否则看到的是
最长一个周期前的旧值）。

| 数据性质                                  | 频次       | 页面隐藏时 | 理由                                         |
| ----------------------------------------- | ---------- | ---------- | -------------------------------------------- |
| 存活 / 就绪探测                           | 30s        | **停**     | 探测对被测方是真实请求，没人看时不该继续打   |
| 累计计数器                                | 60s        | **停**     | 算速率只需两点；更密不会更准，只增负载       |
| 窗口聚合                                  | 手动       | —          | 窗口本身是 1h/24h/7d，秒级刷新没有意义       |
| 注册表 / 配置类                           | 不轮询     | —          | 只在进入页面与写操作后重读                   |
| 明细流（日志 / 审计）                     | 不轮询     | —          | 游标分页，翻页即取；自动刷新会打断正在读的人 |
| **真实上游调用**（模型自检 / 供应商验证） | **仅手动** | —          | **花真钱**，永远只按需触发                   |

上表若靠每页各写一份 `setInterval` 迟早分叉——现在两页已经是同一段代码抄了两遍。
收敛成 `useVisiblePolling(fn, intervalMs)`：隐藏即停、回前台补取、卸载即清，页面只声明频次。

### 7.4 逐页复核结果（2026-08-14，B6-5）

| 数据性质                       | 落在哪几页                                                           | 现状                                                          |
| ------------------------------ | -------------------------------------------------------------------- | ------------------------------------------------------------- |
| 存活 / 就绪探测（30s，隐藏停） | 运行监控 · 服务状态                                                  | ✅ 已换成 `useVisiblePolling`，**真停**                       |
| 状态快照（30s，隐藏停）        | 运行监控 · 任务调度                                                  | ✅ 同上                                                       |
| 累计计数器                     | 运行监控 · 运行指标                                                  | **不轮询**，比上表更保守——见下                                |
| 窗口聚合（手动）               | 模型 / 能力两个用量计量页                                            | ✅ 只在进入与点刷新时取                                       |
| 注册表 / 配置类（不轮询）      | 模型服务、模型路由、两类授权、调用密钥、能力注册、凭证托管、产品三页 | ✅ 进入与写操作后重读                                         |
| 明细流（不轮询）               | 调用日志、变更审计                                                   | ✅ 翻页 / 切流即取                                            |
| **真实上游调用（仅手动）**     | 模型服务页的「验证接入」与「模型自检」                               | ✅ 两者都是**菜单 → 二次确认对话框 → 执行**，没有任何自动路径 |

**「累计计数器不轮询」是有意的偏离，不是漏做**：上表给 60s 是因为「算速率要取两点」。
但运行指标页显示的是**成功率**（successes ÷ attempts）而不是瞬时速率——比率从**单个**
累计快照就能算出来，不需要第二个点。那页自己也写着「不是瞬时 QPS」。为一个用不上的
第二点去起一个定时器，等于凭空给 Atlas 加一份周期负载。真要出速率曲线，正确做法是让
上游导出时间序列，不是在门户里做差分。
