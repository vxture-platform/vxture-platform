## 这份文档是什么

`product_250` 的 **M-3 管理 API 面**只写了一句「结构化错误封套」——**槽位在，内容空**。
本规范补齐那个槽位，并在 v0.3 **合并了消费面**（权威 `product_210`）——一份规范，
**两个维度**：

- **X 组（两面共同）**：错误封套与拒绝词表、`task_id` 归因、审计与计量记录、一词一义与版本
- **M 组（管理面）**：消费方＝运营者与控制台
- **G 组（消费面）**：消费方＝ agent，代表租户与用户
- **D 组（两面共同）**：演进与新产品准入

**判据（v0.3 收紧）：能一致的就该一致。** 全部产品尚无实际用户、零技术与数据债务，
「会破坏现有调用方」这个成本项不存在；只有**传输协议强制**（如 MCP 规定错误进
tool result）或**领域本质**（如能力有依赖闭包而模型路由没有）造成的差异才保留。

**每条自带三产品符合性矩阵**，各仓读自己那一列即可——这是「差异分析」与「明确要求」
的区别所在：审计报告回答「为什么现在是这样」，本规范回答「最终应该怎样、我这个仓要做什么」。

## 四条原则（条款覆盖不到时按这个判）

| #      | 原则                                                                                                                                              |
| ------ | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| **P1** | **每一面的消费方都只有一个**：管理面＝一批运营者；消费面＝ agent（代表租户与用户）。同一个 agent 一次任务里既调能力也调模型，**它不是三个消费方** |
| **P2** | 同一个词、同一个动词，在一个面里**只能有一个含义**                                                                                                |
| **P3** | **静默地做与请求不同的事，比报错更糟**。拒绝可恢复，静默偏离不可                                                                                  |
| **P4** | **能一致的就该一致**——零用户零债务，「破坏调用方」「迁移成本」「先做映射表」当前一个都不成立                                                      |

## 条款索引（正文见 artifact）

**X · 两面共同** — X-1 错误封套与拒绝词表（`NOT_ENTITLED`/`POLICY_DENIED`/`APPROVAL_REQUIRED`/`QUOTA_EXCEEDED` + `retryable`）· X-2 `task_id` 归因 · X-3 审计与计量记录（含 `costUnit`）· X-4 一词一义与版本弃用

**M · 管理面** — 列表反查走参数 · 分页与批量上限 · 动词与语义一致 · 写入结果可分辨 · `state` 枚举 · `DELETE` 只表示移除

**G · 消费面** — 请求元数据（`task_id` 必填，其余永远可选）· 错误承载位置随传输（唯一因协议保留的差异）

**D · 两面共同** — 破坏性变更与弃用 · **新产品 day-one 合规** · 符合性矩阵维护

**保留的豁免六条**，且全部是领域本质或协议规定：`derived` 闭包行 · 撤销快照（**但延迟须在契约里声明**）· MCP 承载位置（**仅豁免位置，封套内容仍受 X-1 约束**）· 计量单位（**仅豁免单位，记录形状受 X-3 约束**）· **atlas 不加 `APPROVAL_REQUIRED` / `POLICY_DENIED`**（v0.4 新增：没有发射点——加一个永不抛出的码，消费方会写一条永不触发的分支，而这正是 X-1 词表规则本身要防的缺陷）。

**v0.3 撤销三条**：「三种错误封套保留」「拒绝码只做映射表」「`subjectRefs` 算特殊」——前两条是拿不存在的迁移成本换的妥协。

## v0.4 —— 上游把活干完了，并纠正/反提了五处（2026-08-17）

10 条 issue 发出后**8 条已关**。上游不只是照做，还推翻了本规范的几处判断——逐条采纳：

| #   | 谁提的    | 规范怎么改                                                                                                                                                                         |
| --- | --------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | atlas#204 | **`costUnit` 由二选一改为开放词表**。`rerank` 按 candidate、`parse` 按 page，塞进 `call` 是**把虚构写进数据**，逼产品在「说谎」与「违规」之间选                                    |
| 2   | atlas#204 | **`actorConsole` 的来源写死**：铸造 OBO 换票的工作台 RP（`act.sub`）。不写清楚，每个仓会各自猜，而猜错的表现是一个永远为 NULL 的列                                                 |
| 3   | atlas#203 | **两条豁免登记**：atlas 不加 `APPROVAL_REQUIRED` / `POLICY_DENIED`——没有发射点。另：本规范原判 `GRANT_DENIED` 是「两义合一」，**实测是错的**，它只有一个含义，正确收敛是一对一改名 |
| 4   | atlas#202 | **`task_id` 只共享键的语义与值，不共享 JSON 路径**。HTTP 面没有 `_meta` 概念，硬造会让它成为请求体里唯一的嵌套异类——判据就是本规范自己那条「承载位置随传输」                       |
| 5   | runos#121 | **X-4 改名不需要三方同时定**。歧义的根源是名字只说了关系、没说对象；说清对象的名字**不可能**与别人撞。等待的成本是「歧义存在的每一天运营者都可能无声读错」                         |

**第 5 条最值得记**：那条纪律是我写宽的。真正管用的规则从来不是「先商量」，是「不许加第 N 个
含义」——而后者用检查比用备注管得住。

另有两条实现取向被上游验证，写进规范作默认建议：**派生优先于物理列**（`state` 从 `is_active`
派生，零 DDL；物理列方案的静默失败是双写窗口内「界面显示已停用而服务继续」），以及
**先收窄类型再改名**（顺序反过来，`if (code === "OLD")` 会安静编译通过）。

## 三条纪律

1. **生效范围分两档**：新增接口即刻适用；存量接口在下一次破坏性变更时迁移。
   不设「全线立即整改」——一份出台当天就有几十处飘红、又没人真去改的规范，只会教会
   大家忽略规范。**但新产品没有这个宽限**（D-2）：那笔债正是「先做再对齐」攒出来的。
2. **逐条签署，不是全有全无**。C-1 改名要三方同时定、可能拖很久；A-1 错误码不该被它卡住。
3. **豁免要登记**。偏离 MUST 须写下产品与业务理由（已登记四条业务差异，见 artifact
   「豁免登记」）。**无理由的偏离视为待改，不是既成事实。**
