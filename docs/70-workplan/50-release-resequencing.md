# 发布节奏重排 · 把一次大爆炸拆成四次可回滚的上线

> **状态**：R0 进行中（2026-08-17 立项）。
> **起因**：一次「升级两个数据库镜像」的请求，查下去发现 **生产落后 main 63 个提交**，
> 而打一个 `v*.*.*` 会把这 63 个提交连同端口重排、DDL 变更**一次性推上生产**。
> **判据**：**每一次上线都必须能单独回滚，并且回滚不需要另一次上线配合。**

## 0. 为什么不能直接打 tag

`deploy.yml` 与 `docker-build.yml` 都由 tag 触发（`dev-*` / `beta-*` / `v*.*.*`），
**镜像从被打 tag 的那个提交构建**。所以「提交什么」＝「发布什么」，中间没有闸门。

生产实况（2026-08-17 经 tailnet 实测）：

|              |                                                              |
| ------------ | ------------------------------------------------------------ |
| 运行镜像     | `v0.20.19`                                                   |
| main 领先    | **63 个提交**                                                |
| 工作区未提交 | **217 个文件**                                               |
| worker-01    | 2 核，**实际可用内存 1607 MB**（标称 2G），swap 2047 MB 未用 |

## 1. 实测出来的四个耦合点

拆分方案不是按提交数切的，是按**耦合**切的。四条耦合决定了顺序：

### ① compose 与镜像被端口重排绑死

那 63 个提交里 `compose.platform.yml` 改了 30 行，**全是端口重排**：
`3040→3030`、`3050→3040`、`3060→3080`、auth-bff `3061→3081`……

所以**不能只发新 compose 配旧镜像**（镜像监听旧口），也不能反过来。
这一条把「基础设施发布」逼到了 `v0.20.19` 那条线上。

### ② auth-bff 的端口迁移——查完发现**没有消费方**

生产现在：`<worker-01-tailnet-ip>:3061`。新 compose：`:8081`（容器内 3081）。

原文这里写「arda 的 handoff 引用着这个口，arda 是外部消费方」，**这是错的**——
`20-arda_100_handoff.md` 里没有任何端口引用。查证结果（2026-08-17 实测）：

| 查法                  | 结果                                                                    |
| --------------------- | ----------------------------------------------------------------------- |
| 生产 established 连接 | **0**                                                                   |
| arda / karda          | 打的是 `<worker-01-tailnet-ip>:8080`（platform-api），**与 3061 无关**  |
| runos                 | 仅 `service/dev/m1-e2e-real.mjs` 一处**注释**，且已自行写明两代端口     |
| nginx                 | 走容器内网名 `vx-platform-auth-bff:3061`，**与 compose 同批改，不脱节** |

runos 那条注释原文：

> Endpoint is `<worker-01-tailnet-ip>:3061` until the L0 port re-map deploys, `:8081` after.

**他们已经知道了，而且那是手工跑的 dev e2e，不是生产运行时。**
compose 里那行注释也把用意写清楚了：「跨仓契约从此只认 80xx，内部重排不再波及产品仓
（原 3090 → 3061 → 本次）」——**这个口已经搬过两次，这次改动本身就是为了让它别再搬。**

**结论：这不是一道门，是一条知会。** 原判「本批唯一一个改了别人会断的动作」不成立。

### ③ DDL 差距**比想象小得多**，而且全是加法

7 个 DDL 文件在 63 个提交里被改过，逐条比对生产库之后，真实差距只有两项：

| 项                                                                    | 生产   | 类型                                |
| --------------------------------------------------------------------- | ------ | ----------------------------------- |
| `product.products` 缺 `origin` / `origin_provider` + 2 CHECK + 1 索引 | 6 行   | **加列**，`DEFAULT 'self'` 自动回填 |
| `provisioning.background_jobs`                                        | 不存在 | **建新表**                          |

其余四项（`perm_name` 64→128 ×2、`subscriptions` CHECK 加 `expiring`、
`voucher_redemptions.redemption_no`）**生产早就有了**——那几处 DDL 改动是在追平现实，
不是在提出新要求。

**结论：这不是一次重建，是一次几十行的前向迁移，零停机。**

### ④ 未提交的 217 个文件——A 与 B **不可分**

| 批  | 内容                                                               | 规模                       |
| --- | ------------------------------------------------------------------ | -------------------------- |
| A   | `portals/opera` · `bff/opera-bff` · `deploy` · `docs`              | 本次会话的一致性工作       |
| B   | `packages/design`(12) · `portals/website`(20) · `portals/admin`(1) | 33 个文件，460 增 / 111 删 |

原文把 B 记为「早于本次会话、状态不明」，并打算让 owner 决定是否挂起。**两点都错**：

**其一，B 是完成的。** `design-system/CHANGELOG.md` 已写好完整条目——含理由、向后兼容
逐条分析（`h-control-xl` → `min-h-control-xl`，单行项零像素差）、以及过渡资产的缩小条件。
`portals/console` 一个改动文件都没有。全量 `type-check:all` 与 `test` 全绿。

**其二，A 依赖 B，挂起 B 会让 A 编译不过。** opera 未提交的改动引用了 B 新增的 API：

| B 新增                  | A(opera) 引用 |
| ----------------------- | ------------- |
| `FieldTier`（新文件）   | **59 处**     |
| `ShellNavItem.subLabel` | **23 处**     |
| `brandPosition`         | 3 处          |

`FieldTier.tsx` 本身尚未跟踪，它的导出行也在 B 的 diff 里——只提交 A，得到的是一个
`import { FieldTier }` 解析不了的树。

**结论：A 与 B 一起提交，不存在「挂起 B」这个选项。**

### ⑤ `3d5ef7c` 会静默打坏 website，而修它的补丁在 B 组里

**这一条是原文完全漏掉的，且是本文里唯一一个「按原计划执行就会造成故障」的耦合。**

`3d5ef7c`（2026-08-07，设计系统重建为 Tailwind v4 原生 token）**不在 v0.20.19，在待发的
63 个提交里**。它退役 legacy token 层时 admin 补了桥、**website 没有**，后果（引 CHANGELOG）：

- 68 个 `--vx-website-*` 版面刻度随文件一起删除 → `min-height` / `grid-template-columns`
  / `padding` 全部 invalid at computed-value time，**栅格塌成单列**；
- `--color-vx-*` 的 `@theme` 注册被删 → 源码里 975 处 `text-vx-*` / `bg-vx-*` 共 123 个
  类名**一个都不再产出 CSS**。

> **两类失效都不报错。**

B 组新增的 `assets/website-tokens.css` 与 `package.json` 的导出入口正是这个桥。

**所以 B 不是「可挂起的无关工作」，是 R3 的硬前置。** 少了它，R3 会把一个当前正常的
生产 website 静默打坏——而这正是 P3「静默地做与请求不同的事，比报错更糟」的教科书形态。

## 2. 四次上线

```
R0 工作区收口 ──► R1 基础设施 ──► R2 DDL 前向迁移 ──► R3 应用发布 ──► R4 一致性工作
   （无上线）      （可独立）        （零停机）         （最大）        （依赖 R3）
```

### R0 · 工作区收口（前置，不上线）

| #    | 任务                                                                | 判据                                 |
| ---- | ------------------------------------------------------------------- | ------------------------------------ |
| R0-1 | ~~确认 B 组是否完成~~ → **已查证：完成，且 A 依赖它**               | 见耦合④⑤。**不挂起，与 A 同批提交**  |
| R0-2 | 按主题分提交：先 B（design 桥与组件），再 A（一致性 / 适配 / 限额） | 一个提交一件事；**B 在前**，A 依赖它 |
| R0-3 | `pnpm type-check:all` + `pnpm test` + 守卫全绿                      | 已跑：tsc 全绿，85+84+93 测试通过    |

### R1 · 基础设施（可独立，最小面）

**只含**：pg `18.4→18.6`、redis `8.8.0→8.10.0`、内存上限重定、新增 `cpus` / `pids_limit`。
**不含任何应用代码。**

因耦合①，从 `v0.20.19` 拉分支，**只搬资源与 digest 那几行，不动端口表**。

| #    | 任务                                                              | 状态                                                          |
| ---- | ----------------------------------------------------------------- | ------------------------------------------------------------- |
| R1-1 | 从 `v0.20.19` 拉 `release/infra-1`，移植 compose 的 digest + 限额 | **✅** `git diff` 只有 image / mem / cpus / pids / 注释行     |
| R1-2 | CI 构建                                                           | **✅ `v0.20.21`**（`v0.20.20` 因下述 CI 缺陷失败，已修）      |
| R1-3 | 部署                                                              | **⏸ 卡在 production 环境的人工审批门**                        |
| R1-4 | 验证                                                              | 15 容器 healthy；`docker stats` 无容器贴顶；pg/redis 版本正确 |

**风险**：整栈重建一次（所有 BFF `depend_on` 库）。**回滚**：重打 `v0.20.19` 的 compose。

#### 顺带修掉的一个 CI 缺陷：镜像只推上去了一半

`v0.20.20` 的 `docker-build` 全线失败：

```
denied: unknown manifest class for application/vnd.oci.empty.v1+json
```

buildx 把 provenance 与 SBOM 作为**独立 manifest** 一起推，其 config 媒体类型是
`application/vnd.oci.empty.v1+json`。**GHCR 认，阿里云个人版 registry 不认**——所以现象
是「推上去了一半」：ghcr 有这一版、阿里云没有，而**生产拉的正是阿里云那份**。

不是这批改动引起的（这批只动 compose，碰不到 Dockerfile；action 也钉着 SHA）。
最后一次成功构建是 2026-08-09，其间 runner 的 buildkit 升级把这两项转成了默认开启。
已在两处 build step 上加 `provenance: false` / `sbom: false`。

## 3. 两条贯穿的纪律

**每次只改一个变量。** R1 只动基础设施、R2 只动 schema、R3 只动应用、R4 只动一致性。
出事时「刚才改了什么」永远只有一个答案——这是拆分的全部收益，比省下的停机时间值钱得多。

**先查生产再写计划。** 本文里每一个数字都是实测的。**本文有三处判断被后续查证推翻，
全部保留原文并标注**，因为推翻它们的方法比结论更值得留下：

| 原判                        | 查法                          | 实际                         |
| --------------------------- | ----------------------------- | ---------------------------- |
| DDL 是个迁移项目            | 逐条比对生产库                | 两条加法，零停机             |
| 3061 有跨仓消费方，需对表   | `ss` 看连接 + grep 四个兄弟仓 | 零消费方，runos 早已自行写明 |
| B 组状态不明，待 owner 决定 | 读 CHANGELOG + 查 A 的引用    | **B 已完成，且 A 依赖它**    |

后两条原本都被记成「待 owner」。**它们不是 owner 的问题，是没查。** 把可查的东西挂成
待办交出去，等于让计划停在自己偷懒的地方——而第三条一查还牵出了耦合⑤，
**那是本文唯一一个会真的造成生产故障的点。**
