# 发布节奏重排 · 把一次大爆炸拆成四次可回滚的上线

> **状态**（2026-08-17）：R0 ✅ · R1 ✅ 已上线（`v0.20.22`）· R2 ✅ 已上生产
> · R4 的 DDL ⏸ 待执行 · R3+R4 应用发布 ⏸（两批已合并成一次，见 §2）。
> **起因**：一次「升级两个数据库镜像」的请求，查下去发现 **生产落后 main 63 个提交**，
> 而打一个 `v*.*.*` 会把这 63 个提交连同端口重排、DDL 变更**一次性推上生产**。
> **判据**：**每一次上线都必须能单独回滚，并且回滚不需要另一次上线配合。**

## 0. 为什么不能直接打 tag

`deploy.yml` 与 `docker-build.yml` 都由 tag 触发（`dev-*` / `beta-*` / `v*.*.*`），
**镜像从被打 tag 的那个提交构建**。所以「提交什么」＝「发布什么」，中间没有闸门。

生产实况（2026-08-17 经 tailnet 实测）：

|              |                                                              |
| ------------ | ------------------------------------------------------------ |
| 运行镜像     | `v0.20.19`                                                   |
| main 领先    | **63 个提交**                                                |
| 工作区未提交 | **217 个文件**                                               |
| worker-01    | 2 核，**实际可用内存 1607 MB**（标称 2G），swap 2047 MB 未用 |

## 1. 实测出来的耦合点

拆分方案不是按提交数切的，是按**耦合**切的。下面五条决定了顺序；**第六条是执行时才
撞出来的**（主机 runtime env ↔ 审计脚本），记在 §2 的 R1 那节，因为它是被一次失败的
部署教出来的，不是坐在这里想出来的。

### ① compose 与镜像被端口重排绑死

那 63 个提交里 `compose.platform.yml` 改了 30 行，**全是端口重排**：
`3040→3030`、`3050→3040`、`3060→3080`、auth-bff `3061→3081`……

所以**不能只发新 compose 配旧镜像**（镜像监听旧口），也不能反过来。
这一条把「基础设施发布」逼到了 `v0.20.19` 那条线上。

### ② auth-bff 的端口迁移——查完发现**没有消费方**

生产现在：`<worker-01-tailnet-ip>:3061`。新 compose：`:8081`（容器内 3081）。

原文这里写「arda 的 handoff 引用着这个口，arda 是外部消费方」，**这是错的**——
`20-arda_100_handoff.md` 里没有任何端口引用。查证结果（2026-08-17 实测）：

| 查法                  | 结果                                                                    |
| --------------------- | ----------------------------------------------------------------------- |
| 生产 established 连接 | **0**                                                                   |
| arda / karda          | 打的是 `<worker-01-tailnet-ip>:8080`（platform-api），**与 3061 无关**  |
| runos                 | 仅 `service/dev/m1-e2e-real.mjs` 一处**注释**，且已自行写明两代端口     |
| nginx                 | 走容器内网名 `vx-platform-auth-bff:3061`，**与 compose 同批改，不脱节** |

runos 那条注释原文：

> Endpoint is `<worker-01-tailnet-ip>:3061` until the L0 port re-map deploys, `:8081` after.

**他们已经知道了，而且那是手工跑的 dev e2e，不是生产运行时。**
compose 里那行注释也把用意写清楚了：「跨仓契约从此只认 80xx，内部重排不再波及产品仓
（原 3090 → 3061 → 本次）」——**这个口已经搬过两次，这次改动本身就是为了让它别再搬。**

**结论：这不是一道门，是一条知会。** 原判「本批唯一一个改了别人会断的动作」不成立。

### ③ DDL 差距**比想象小得多**，而且全是加法

7 个 DDL 文件在 63 个提交里被改过，逐条比对生产库之后，真实差距只有两项：

| 项                                                                    | 生产   | 类型                                |
| --------------------------------------------------------------------- | ------ | ----------------------------------- |
| `product.products` 缺 `origin` / `origin_provider` + 2 CHECK + 1 索引 | 6 行   | **加列**，`DEFAULT 'self'` 自动回填 |
| `provisioning.background_jobs`                                        | 不存在 | **建新表**                          |

其余四项（`perm_name` 64→128 ×2、`subscriptions` CHECK 加 `expiring`、
`voucher_redemptions.redemption_no`）**生产早就有了**——那几处 DDL 改动是在追平现实，
不是在提出新要求。

**结论：这不是一次重建，是一次几十行的前向迁移，零停机。**

| 批  | 内容                                                               | 规模                       |

**结论：A 与 B 一起提交，不存在「挂起 B」这个选项。**

#### R-3 的 DDL 不是纯加法，而且查出一条与安全相关的前提

脚本：`deploy/database/migrations/2026-08-17-R4-audit-console-stepup-and-oidc-state.sql`

生产实测差距：`support.audit_logs.actor_console` 无、`admin.operator_permission
.requires_step_up` 无、`appoidc.oidc_clients` 的 CHECK 仍是 `('active','disabled')`
且**有 2 行是 `disabled`**。第三项要「卸 CHECK → UPDATE → 建新 CHECK」，三步同一事务。

**顺序为什么是 DDL 先行，以及为什么这次安全**：先做 DDL 意味着旧镜像会看到一个它不
认识的 `inactive`。查了生产在跑的 `PgOidcClientRepository`，三处过滤**全是
`status = 'active'`**，不是 `status <> 'disabled'`——所以那两行改值后仍不等于 `active`，
不会被放开。**若当初写的是后者，这一步就会在窗口期把两个已停用的 OIDC 客户端悄悄
放开。** 那是安全洞不是排版问题，所以这条判断查过才动手，并写进了脚本注释。

反序的后果同样不是「审计少几行」：新镜像每一次写都要往 `audit_logs` 插一行带
`actor_console` 的记录，列不存在则 insert 失败，而**审计写在业务写的同一个事务里**，
业务写跟着回滚——表现是所有写操作都失败。

#### 第一次打 tag 撞出的第三个基础设施缺陷：一步静默空转的依赖预构建

`v0.20.23` 的 `docker-build` 里五个前端全线失败（BFF 全过）：

```
Module not found: Can't resolve '@vxture/design-ui'
  ../../packages/design/design-system/src/components/auth/AuthLogin.tsx
```

`Dockerfile.nextjs` 有一步预构建门户的工作区依赖，写的是：

```dockerfile
RUN pnpm --filter "...^${PACKAGE_FILTER}" --if-present build   # 空集
```

**选择器方向写反了，而写反不报错**——pnpm 对空集只说一句 `No projects matched the
filters` 然后成功退出。实测：

| 写法                | 匹配  |
| ------------------- | ----- |
| `...^@vxture/opera` | **0** |
| `@vxture/opera^...` | **5** |

`^` 在左边是「依赖方」（谁依赖它），门户没有依赖方，所以是空集；`^` 在右边才是
「被依赖方」。旁边那行注释写的正是后者的意思，代码用的是前者。

**这一步一直在空转，只是以前看不出来。** 三包拆分之前，`design-system` 由门户
alias 到源码消费，没有任何依赖需要 dist；拆分后 `design-ui` / `design-tokens` 经
`exports` 走 `dist/`，而 `.dockerignore` 排除 `**/dist`——dist 只可能来自这一步。
它一空转，dist 就必然缺。

**为什么本地与 CI 的 `build` 都是绿的**：两者都在完整 workspace 上装完再构建，dist
早就在了。只有 Docker 那条「干净上下文 + 排除 dist」的路径会暴露它。

#### 修好那一步之后，它替谁挡了枪立刻现形

`v0.20.24` 带上修复重发，`design-ui` 那条报错消失——**然后当场冒出两个新的**。
两个都是老问题，一直藏在空转背后：

**其一，五个门户里只有一个 alias 写对。** 报错
`Can't resolve '@vxture/design-system/styles/fonts.css'`。webpack 的 alias 默认前缀
匹配，而这一条的值是个**文件**（`client.ts`）不是目录，于是子路径被改写成
`…/src/client.ts/styles/fonts.css`，必然解析失败。加 `$` 精确匹配才只让裸包名走 alias。

**这个修复此前只打在 website 一个门户上**——把病因说得明明白白的那段注释就写在
website 的 config 里，另外四个照旧。`opera` / `admin` / `console` / `accounts` 现已
补齐。

**其二，`@vxture/platform-browser` 根本不可构建。** 它是整个 workspace 里**唯一有
`build` 脚本却没有 `tsup.config.ts`** 的包，tsup 只会说 `No input files` 然后失败；
而它的 `package.json` 声称 `main: dist/index.js`——**一个指向从不存在的产物的入口
声明**。三个消费方门户都把它 alias 到 `src`，所以谁也没被它绊过。

补配置而不是删 build 脚本：删了会让 `main` / `types` 那两行继续说假话，那是留给下一个
人的陷阱。已验证 `main` 指向的文件现在真的存在。

#### 构建过了，部署又栽在一行 `cd` 上

`v0.20.25` 的 `docker-build` 全绿，部署跑到这里停下：

```
bash: scripts/15-migrate-runtime-ports.sh: No such file or directory
Process exited with status 127
```

`deploy.yml` 里那行用**相对路径**调脚本，而 `cd "$DEPLOY_DIR"` **在下一行才执行**——
相对路径于是在 SSH 登录默认目录（`$HOME`）里找。已改成绝对路径，不依赖工作目录。

诊断时差点被一个巧合带偏：紧邻的上一句日志是
`[ok] runtime .env inter-service names migrated to vx-platform-*`，看着像「14 号脚本
能跑、15 号找不到」。**但那句来自内联的 sed 块，不是脚本文件**——两者根本不在同一种
调用方式上，可比性是假的。

`15-` 是 2026-08-10 新增、从未部署过的脚本，所以这条路径假设一直没被走过。

#### 一条模式：五次失败没有一次是应用代码的问题

| #   | 缺陷                                     | 伪装成             |
| --- | ---------------------------------------- | ------------------ |
| 1   | 阿里云 registry 拒收 provenance manifest | 构建失败           |
| 2   | env 审计脚本落后于主机 runtime env       | 部署失败           |
| 3   | 依赖预构建选择器方向写反，静默空转       | `Module not found` |
| 4   | alias 只修了一个门户 + 一个不可构建的包  | `Module not found` |
| 5   | 部署脚本用相对路径，而 `cd` 在下一行     | 找不到文件         |

**第 4 条是被第 3 条掩盖的**——一个静默的空操作，替两个真问题挡了不知多久。
其余四条的共同点是：**都是从没被执行过的路径**。1 与 5 是新代码第一次跑，
2 与 3 是老代码第一次真的被走到。

这也是这份计划反复撞上的同一件事：**不报错的失败最贵**。而这一整串换来的具体好处，
正是开篇那条判据兑现的样子：**五次失败全部落在构建与部署阶段，生产始终跑着一个完整
可用的版本**，没有一次半上线状态需要抢修。

## 3. 两条贯穿的纪律

**每次只改一个变量。** R1 只动基础设施、R2 只动 schema、R3 只动应用、R4 只动一致性。
出事时「刚才改了什么」永远只有一个答案——这是拆分的全部收益，比省下的停机时间值钱得多。

**先查生产再写计划。** 本文里每一个数字都是实测的。**本文有三处判断被后续查证推翻，
全部保留原文并标注**，因为推翻它们的方法比结论更值得留下：

| 原判                        | 查法                          | 实际                         |
| --------------------------- | ----------------------------- | ---------------------------- |
| DDL 是个迁移项目            | 逐条比对生产库                | 两条加法，零停机             |
| 3061 有跨仓消费方，需对表   | `ss` 看连接 + grep 四个兄弟仓 | 零消费方，runos 早已自行写明 |
| B 组状态不明，待 owner 决定 | 读 CHANGELOG + 查 A 的引用    | **B 已完成，且 A 依赖它**    |

后两条原本都被记成「待 owner」。**它们不是 owner 的问题，是没查。** 把可查的东西挂成
待办交出去，等于让计划停在自己偷懒的地方——而第三条一查还牵出了耦合⑤，
**那是本文唯一一个会真的造成生产故障的点。**
