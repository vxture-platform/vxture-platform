所以原计划那句「内部产品可能本来就不接 C3」**不成立**——切分维度根本不是内外，
而且**第五项在每一个真实产品上都已经通过**。盘点表里「对 14 个产品必然不过」字面为真
但没有运营意义，**「不适用」分支也不必加**：不存在一个真实产品需要它。

**真正的缺陷在别处**：第五项失败时给的 remedy 原文是「webhook 登记目前没有界面入口，

`@Get(":id/webhook")`，没有任何写端点，opera 也没有任何页面写它。**一个检查项失败后
让运营者去手改数据库，这个闭环是断的。** 这才是 D3-1 该做的事。

#### D3-2 · 检查单 —— 平台侧不需要「勾」，对方侧是真没做

全库只有 4 行，且全在那两个冒烟产品上：`catalog_registered` ×2（都满足）、
`c1_identity` ×2（都不满足）。7 个真实产品**零行**。

但这不是空缺：**平台侧五项是读时从真实数据推导的**（`launch-checks.ts`），只有
`catalog_registered` 回写。所以「从未勾过」正是平台侧应有的状态——页面自己算，无从补起。

真正缺的只有对方侧三项（`c1_identity` / `c2_entitlement` / `c3_metering`），而那是
**一次运营确认行为**（「对方确实做完了它那半」），不是我能灌的数据。灌进去等于制造
假绿灯——正是先前修掉的那个缺陷。

#### D3-1' 完成记录

| 层     | 内容                                                                               |
| ------ | ---------------------------------------------------------------------------------- |
| BFF    | `PUT product/catalog/:id/webhook`——upsert（`product_id` 是 PK），`assertCanManage` |
| 界面   | 产品目录行操作新增「Webhook 登记」，两档弹窗（回调地址 + 密钥引用 / 产品主页）     |
| 检查项 | remedy 改成真实做法；`href` 从 `/ops/logs` 改为深链回产品目录                      |

几个判断：

- **三项都允许留空**（DDL 三列都可空）。运营者常常先拿到回调地址、密钥引用还没签发，
  这时要能先存一半——不给存就是把人推回手改库，正是这一条要消灭的东西。检查项本来就
  区分「没有登记行」「配了一半」「配齐」三种态，写入侧不该把中间态堵死。
- **非空才校验格式**：地址必须是 http/https 绝对 URL，长度按 DDL 的 512 / 128 拦成 400
  而不是让数据库拒成 500。密钥**引用**不做 URL 校验——它是取密钥的路径不是密钥本体。
- **先读回现状再开弹窗，读失败就不给填**：这是 upsert，对着三个空框保存会把读不出来的
  那份覆盖成空。读失败时弹窗里出的是空状态而非表单。
- **产品不存在回 404 不回 500**：FK 违例会冒成 500，而真实答案是产品码错了——报成服务器
  错误会让人去查服务。
- 入口独立成一项而不塞进「编辑」：webhook 是产品级**接入配置**，与目录属性不是一回事。
- 图标用 `plug`（DS 里没有 webhook 图标），与 provider 的 `plugs-connected` 区分。

opera / opera-bff type-check + lint 全过；upsert 的 `ON CONFLICT` 在事务里跑通后回滚，
未留数据（`product_webhooks` 仍 7 行）。

**未验**：新端点要等 opera-bff 重建后才在运行实例上生效（它跑的是 `dist` 打包产物）。

### E2 · derived 两级行 —— ✅ 已完成（2026-08-16）

一条 direct 是父行，它推导出的 derived 是子行。arda 的 4 条授权收起后读作 **3 行**，
「故障复盘」带标注「带 1 条派生」并出箭头；另两条没有派生**就不出箭头**——一个点了
没反应的箭头比没有箭头更让人以为是坏的。

**形态与「运行监控 · 服务状态」一致**：拉平成一个行集、同一套 `columns` 渲染两种行，
列位置由结构保证，不做嵌套表（嵌套要靠占位格数 + 固定列宽 + 隐藏表头三层补丁去凑对齐，
每层都能单独失配）。

**派生行给的是「撤销它的锚点」，不是禁用的撤销**。它确实撤不掉（runos 刻意不级联），
但运营者真正想做的事有出口——撤掉锚点，闭包重编译时这一条自然消失。给一个灰掉的按钮
等于把人堵在那儿。父行那条相应标成「撤销授权（连带 N 条派生失效）」，把后果写在动作上。

**孤儿 derived 照样出行**（锚点不在本主体——理论上不该发生）：把一条运营者确实持有的
授权因为归不了组就从界面上抹掉，比多出一行难解释得多。这种行的菜单项标「锚点已不在
本产品」并禁用，因为此时确实没有可撤的对象。

- `model/grants` 的四项**全部可选**（应用 ID / 应用类型 / 到期 / 理由）——它本来就是
  一档，分档没有可分的东西。
- `model/routes` 在 `routeOnly` 下只剩两个字段，档头会比内容还高。
- 确认框与密钥回显框一律不分档（此前已定）。

**顺带修掉一个门禁漏洞**：注册 Capability 的 `分类` 标签与说明都写着「必填」，
`draftValid` 却没拦，运营者能一路点到「注册」再吃一个服务端报错。要么拦要么别写
必填——这里选拦。

#### E3-2 · 挡位接错了一次

`Drawer.width` 我第一版接的是 `OverlayWidth`。那道梯是给下拉与气泡的，最宽一档 `xl`
只有 **384px**（`layout-semantic.css` 自己的注释就写着「再宽应分栏或改用 panel」），
而四个抽屉全在 500px 以上。接上去的后果是：谁写 `width="xl"` 就得到一个被腰斩的面板，
**而且不报错**。已改为 `DrawerWidth`（panel 梯 sm 448 / md 512 / lg 672），四处调用点
从 `width={560}` / `width={520}` 统一为 `width="md"`，并在 `width` 的注释里写明不要
再接回 overlay 梯。

#### E3-3 · 复核结果

没有页面自己写弹窗滚动容器或自定义页脚。剩下 3 处 `max-h-[Nvh]` 是**弹窗内部的选择
列表**（多选 endpoint / 多选能力），属于正当的嵌套滚动区，不是重写 `DialogForm` 的
职责；但三处高度原本是 32 / 36 / 32 三个各写各的值，已统一为 32vh。
