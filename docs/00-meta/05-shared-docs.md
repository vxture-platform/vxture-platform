# 跨仓共享文档索引

> **这里只有指针，没有正文。**
>
> 需要被**多个仓同时引用**的文档（跨仓契约、规范、审计结论）正文放在 Claude
> artifact，各仓只指向。理由：这类文档一旦在每个仓存一份，**必然各自漂移**，而漂移
> 的表现是「两处权威」——本仓已经在 DDL 上吃过这个亏（见
> `deploy/database/ddl/60_model.sql` 抬头的「不得同时保留两处权威」）。
>
> **判据**：只有本仓消费的文档留在本仓；被两个及以上仓引用的，正文出仓、本仓留指针。

**要求只有一处。** ① 回答「最终应该怎样、我这个仓要做什么」，② 回答「为什么现在是这样」。
①a 不回答任何问题，它只是把旧条款号接到 ① 上。

**2026-08-29 的教训：「指针文件」写着写着会长成第二份正文。** `product_251` 的仓内指针
开篇就声明「本文只是仓内指针」，却带着四条原则、条款索引、豁免摘要和两轮变更判定——
**声明自己是指针不等于是指针**。判据很简单：**指针文件里不应该有任何一句话是「要求」**。

两章的**判据不同**，这是刻意的：管理面的消费方是一批运营者，**形状也该收敛**；
消费面的消费方是 agent（代表租户与用户），**同一个 agent 一次任务里两边都调**——
所以它也是一个消费方，判据同样是「能一致的就该一致」，只有**传输协议强制**
（MCP 规定错误进 tool result）与**领域本质**（能力有依赖闭包）才保留差异。

> 原独立的「消费平面审查」artifact 已并入 ② 的 CH.2，原地址只保留跳转不留副本
> ——留完整副本就是两处权威。

## 加一份共享文档时

1. 正文写成 artifact，与既有两份保持同一套版式（便于并排阅读）。
2. 在本表加一行。
3. 仓内建一个**指针文件**：只放定位、边界、回指与索引级摘要（如条款号表），**不复制正文**。
   **自查一句**：如果删掉这个文件，有没有任何一条「要求」会跟着消失？会 → 它已经是第二份正文了。
4. 若它约束其它仓，在对应的既有契约里加一行指过去（如 `product_250` M-3 指向接入通则），不新立权威。
5. **符合性不写进文档。**能机器判的做成守卫脚本 + 快照比对；判不了的（语义类）明说靠评审。
   写死在文档里的符合性是快照，会烂——而且烂了不报错。

## 为什么不是仓内 + 定期同步

同步靠人记，而漂移无声。共享文档的读者分布在多个仓、多个 owner，**没有任何一个人有动机
去核对另外两个仓里的副本是否还一致**——所以不设副本。
